# Nexus 未来六个月实施路线图

建设输入为约 10 人团队、工业控制与设备联网、STM32/GD32 等 MCU，以及 3–6 个月周期。首个 3 个月交付目标是一个参考组合的受控产品试点；6 个月目标是两个 MCU 平台共享应用与契约、具有可追溯交付和现场恢复能力的企业候选。具体系列、板卡、控制周期、通信接口与 OTA 空间应在首个迭代确定。

“企业候选”表示具备明确支持矩阵和试点证据，不等于所有芯片支持、行业认证、长年 LTS 或无人维护。阶段延期时按产品价值和风险缩减范围，不能降低控制安全、持久化完整性或发布证据要求。参考 [任务清单](backlog.csv) 和 [质量标准](quality-security.md) 判断完成。

## 团队分工

| 角色 | 人数 | 主责 | 主要协作 |
|---|---:|---|---|
| 平台技术负责人 | 1 | 架构、公共契约、需求范围、ADR、跨模块集成 | 产品负责人、各模块 owner；兼任安全决策协调 |
| 内核与公共接口 | 2 | HAL/OSAL、设备生命周期、并发、内存、时间与 DMA 契约 | BSP、应用和 QA |
| 平台与板级适配 | 2 | 一人主 STM32、一人主 GD32；启动、时钟、驱动、板卡、Flash | 相互 review，QA 共用契约测试 |
| 工业应用与通信 | 2 | 参考应用、采集控制、Modbus/RS485、按需 CAN/网络 | 需求与 BSP；兼任产品参数和现场行为 |
| 质量与硬件验证 | 2 | 契约/SIL、HIL、故障注入、资源与时序测量 | BSP、应用；保留独立验证视角 |
| 构建与发布工程 | 1 | 配置、CI、依赖、工件、SBOM、签名集成和发布证据 | QA 与负责人；工具不可仅由一人理解 |

安全、制造和客户现场职责需要企业相关人员参与，并在 10 人研发中设接口人；不假定另外已有专职团队。每个关键模块至少有一名副 owner，避免板卡、签名或发布成为单人瓶颈。上述分工可按成员经验调整，责任不能通过调整变得无人承接。

采用 2 周迭代，每次只选择可集成、可验证的垂直任务。初始保留约 30% 容量用于缺陷、集成、review 和硬件等待，这是排期假设，4 周后按实际吞吐校准。核心改造同时在制不超过 2 条，BSP 两通道可并行，服务功能应等待所依赖接口和预算稳定。

## 阶段与退出标准

| 周期 | 交付范围 | 完成条件 | 未完成时的处理 |
|---|---|---|---|
| 第 1–2 周 | 固定基线、恢复 CI、选择 2 个参考板、建立需求/支持矩阵、关闭假成功 | 干净 checkout 的 Native 与 STM32 ARM 能构建；实际测试数量和失败可追溯；有效配置与编译 flags 一致；GD32 选型和 bring-up 清单确定；发布失败不产生正式版本 | 暂停新功能；保留候选状态，不以文档指标替代执行结果 |
| 第 3–6 周 | HAL/OSAL 契约、临界区端口、SPI/UART DMA 生命周期；STM32 完成核心链路，GD32 启动/时钟/GPIO/UART；HIL 上线 | 同一契约套件在 Native/目标后端通过；ISR API 与优先级正确；DMA 超时/取消/错误只产生一次终态；两个板卡可自动刷写、识别和恢复 | 延后高层协议；按驱动逐项提升支持等级，不整个平台一次性标绿 |
| 第 7–12 周 | 工业参考应用、RS485/Modbus、看门狗、真实参数存储、现场诊断；GD32 复用应用 smoke | 一个参考组合达到控制时序及资源预算；存储任意注入点断电恢复；业务异常有确定降级；试点镜像及报告完整；GD32 仍不足时限定首个试点范围 | 第 3 个月交付受控试点，不扩大到未经验证的板型和远程更新 |
| 第 13–18 周 | GD32 同契约与应用闭环；按产品选择 CAN/网络；熵源、crypto provider、boot/OTA、设备身份 | 两平台运行相同产品用例；DMA/Flash/IRQ 差异已验证；安全更新的篡改、错板、断电和恢复测试通过；容量不足时采用外部存储/维护升级方案 | OTA 或网络高层功能可推迟；维持已有安全的本地升级和恢复渠道 |
| 第 19–24 周 | 量产烧录校准、候选灰度、兼容迁移、依赖/许可/SBOM、现场故障演练和发布治理 | 两参考组合的支持矩阵、证据包和已知问题齐全；制造可追溯；试点反馈形成回归；升级/回退/维修演练完成；补丁责任、回归资源和支持周期有承接 | 发布企业候选并限制范围；正式支持与 LTS 由证据、人员和预算决定 |

前 6 个月不默认纳入新的 MCU 大族、完整 RT-Thread/Zephyr 后端、TinyML、云厂商大全、复杂 GUI 或行业认证。需要其中某项的实际产品可以重新排序 backlog，但应换出同等容量工作，不能累加到原承诺上。

## 两条平台通道的协作

STM32 通道以当前代码资产恢复基线，GD32 通道先建立差异清单和最小 bring-up。公共接口 owner 提供同一套行为契约及 Native 测试模型；两个 BSP owner 各自实现，不把 ST HAL 类型泄漏到 GD32 或通用层。GD32 系列未确定前，仅做端口模板和评估，不制造虚假的全系列支持。

首发板选择至少比较可获得性、生命周期、调试接口、Flash/RAM 预算、RS485/CAN/Ethernet 外设、DMA/cache、watchdog/brownout、量产工具、SDK 许可与团队熟悉程度。两个板卡不必功能完全相同；核心公共用例必须相同，平台差异以 capability 查询及 profile 约束表达。

每个 PR 跑受影响的契约和编译组合；每日跑完整 Native 和两个板 smoke；每周跑断电、压力和长时间运行，进入候选前跑完整产品矩阵。执行频率要由 HIL 池容量校准；自托管 runner 不直接执行未经信任的外部 PR，先在隔离环境验证再使用受控镜像进入实验室。

## 工业参考产品验收

| 需求 | 必须定义的输入 | 验收结果 |
|---|---|---|
| 控制实时性 | 周期、允许抖动、最坏通信/存储负载、任务和 ISR 优先级 | 目标板在最坏规定负载满足时限；波形和测试配置可复现 |
| 通信恢复 | RS485 帧间隔、链路丢失判据、重连、CAN bus-off 策略 | 断线、噪声、忙总线不拖垮控制；错误可观察且恢复有上界 |
| 参数完整性 | Flash 几何、记录大小、写频率、工厂参数和运行参数权限 | 任意写/擦除中断后读取完整旧/新状态；损坏拒绝或安全降级 |
| Watchdog | 业务健康判据、卡死任务、复位后安全状态 | 业务停止时能触发恢复；不能仅由独立喂狗任务证明健康 |
| 更新恢复 | 分区容量、维护窗口、最低允许版本、现场离线条件 | 镜像认证、错板拒绝、断电恢复与允许回退通过；控制窗口限制明确 |
| 制造维护 | board revision、序列号、校准、设备身份、工装版本 | 每台设备能关联交付镜像；返修和凭据变更可审计 |

控制周期、抖动、RAM、Flash、功耗和恢复时间不使用统一虚构值。在第 1–2 周形成产品 budget；随后所有性能趋势都附测量方法、参考板、编译配置和绝对预算。覆盖率用于识别盲区，不能代替上述结果。

## 研发管理节奏

每周进行一次 30–45 分钟跨模块集成检查，集中处理契约、依赖、板卡和发布阻塞；每两周用真实演示和测试报告验收一次增量；每月评估产品范围与风险，并校准 3–6 个月路线。日常任务用 Issue 与 PR 管理，不为小修复增加会议。

需求记录具体触发、预期行为、失败行为、资源约束与测试 ID。接口、存储、启动、安全和发布架构变更写 ADR；PR 附影响矩阵、验证和迁移说明。平台/BSP/产品通过版本约束和兼容清单协调，不允许产品长期复制整个框架形成无法维护的私有分叉。

先持续采集构建成功率、实际测试数量、flake、PR 等待时间、缺陷逃逸、现场复位与升级各阶段结果，前 4 周建立基线。随后设置目标与趋势，不用提交量、代码行数或新增 MCU 数量考核个人。任何门禁豁免都有责任人、期限和补偿措施；空测试、未授权镜像和无法恢复的核心缺陷不能通过豁免变成“已验证”。

## 第一个迭代的任务顺序

1. 复核本次候选补丁，在完整 checkout 与 pinned submodules 上运行 CI，保存现有失败，不直接发布正式版。
2. 完成有效配置生成到 build 目录、Native 临界区和 SPI 编译契约，修正后恢复主机构建和目标编译。
3. 选定 STM32/GD32 两个具体型号与参考板，冻结第一版产品 budget 和通信优先级。
4. 将支持矩阵和 backlog 与真实 owner 对应；搭建首个可自动识别、刷写、复位和采集串口的 HIL 设备。
5. 演示一个完整用例：参数读取、GPIO/UART 动作、错误检测、watchdog 恢复和产物追溯；下一迭代补真实采集与通信。
