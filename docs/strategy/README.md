# Nexus 工业嵌入式平台建设方案

Nexus 的首期定位是服务工业控制与设备联网的 MCU 软件平台。建设目标是让多个产品和板卡复用可靠的驱动、操作系统适配和设备服务，并形成从需求、验证、发布到制造与现场维护的完整证据链。优先完成一个参考硬件组合的闭环，再扩展芯片和协议；接口数量、测试数量与文档数量不能替代设备运行证据。

当前源码审查基线是 `7a203266082ad1f655b6686713b2b7950ba31ec6`，日期为 2026-10-08。用户已确定约 10 人团队、STM32/GD32 等平台和 3–6 个月建设周期。以下架构和企业流程属于建设方案；本地首批修复的验证范围单独记录在 [首批迭代记录](first-iteration.md)。具体参考板、控制周期和首发产品功能尚未确定，里程碑以验收条件为准。

## 当前判断

项目已经具备 HAL 能力接口、OSAL 适配框架、Native 模拟，以及 Config、Log、Shell、Init 等模块，值得继续建设。工业产品采用前的主要阻碍是构建配置与接口契约未统一、真实平台实现范围与文档不一致，以及硬件验证和发布门禁不足。首期采取增量改造，保留可用的 C 接口和测试资产，逐步补齐边界。

已核查的关键问题包括：

- Native 构建读取仓库 STM32 配置；工作流引用不存在的 ARM preset；多重 preset 继承让宿主默认值覆盖目标值；生成头文件和有效构建配置需要进一步统一。
- Native/GD32 等平台 CMake 仍引用仓库中缺失的 `NexusLinkerConfig` 模块及旧的 `nexus_apply_compiler_config/linker_config` 入口，构建接口需要同步。
- STM32 SPI 对当前 OSAL 的函数名称和信号量参数存在漂移；超时、DMA 停止、完成回调和错误传播尚未形成完整契约。
- HAL 临界区仅按 GCC/Clang 编译器判定 ARM 指令。在 x86 GCC 上启用线程安全后，单文件编译已复现 `primask/cpsid` 汇编错误。
- 配置加密使用由密钥派生的确定性 PRNG，缺少认证；密钥轮换只改密钥而未迁移旧值；Flash 后端仍为 RAM 模拟。
- 现有发布流程在构建前公开 Release，检查中存在吞失败行为；README 的支持等级和指标不能作为当前成功执行证据。

完整证据及影响见专项文件。潜在竞态、DMA 使用错误和安全风险按静态分析结论管理，需要针对性的运行验证；单文件编译失败、明确的 TODO 和工作流依赖关系属于可直接核查的事实。

## 首发产品范围

首期建立 Native + 一个 STM32 参考板 + FreeRTOS/裸机验证组合，同时准备一个 GD32 参考板的移植通道。现有 STM32F407 配置可作为候选，但最终系列、板卡、Flash 容量、通信器件和量产条件需由实际产品确定。GD32 的启动、时钟、IRQ、DMA 和 Flash 需要独立验证，不能因引脚或寄存器相近就宣布兼容。不要把芯片型号等同于受支持板卡，也不要将当前候选描述为已完成硬件验证。

工业参考应用包含采集、控制状态机、设备通信、持久化参数、看门狗与恢复诊断。优先把 GPIO、UART、SPI 和基础定时链路验证清楚，然后按产品需求引入 RS485/Modbus、CAN 或 Ethernet。协议服务、TLS、设备身份和 OTA 为按需模块；并非所有小型设备都需要同一组功能。

控制路径采用有界执行、明确资源预算和故障安全状态。联网、日志、Shell、配置提交和升级采用独立任务、队列和优先级，不能无限占用控制任务的锁、CPU 或存储资源。若 Flash 擦写会阻塞指令获取，产品必须规定维护窗口或使用满足时序的存储布局。任务隔离本身不等同于内存隔离或功能安全隔离。

## 企业平台的完成标准

企业能够交付的不只是一个固件，而是一个被支持的组合：产品版本、板卡 revision、SoC、RTOS、工具链、最终配置、依赖 commit 和已验证镜像。每个组合有清晰的支持等级、测试记录、资源预算、已知问题及生命周期责任人。

正式发布使用已验证的同一组产物，保存 ELF、镜像、map、配置、依赖清单、SBOM、测试与 HIL 报告、摘要和签名；制造与升级记录关联这些身份。现场故障通过镜像和符号还原，再转为回归测试和补丁。平台、BSP、产品应用可以采用不同版本节奏，但必须有可机器校验的兼容矩阵。

统一流程支持不同风险：日常可逆改动走简洁 PR 和自动检查；公共接口、持久化格式、启动链和现场更新变更需要 ADR、迁移策略和对应验证；行业安全要求另行建立危害分析、资格与认证活动。平台建设不能自行替代产品的安全责任。

## 接下来的实际顺序

先恢复可重复的 Native/ARM 构建和真实门禁，冻结 HAL/OSAL 生命周期、ISR、超时与 DMA 契约；接着接入 STM32/GD32 参考板及故障注入 HIL，再完成工业参考应用、持久化和安全更新。约第 3 个月以一个平台的受控产品试点为目标，第 6 个月以双平台企业候选和量产维护闭环为目标。只有经过试点和持续回归资源确认后，才承诺企业支持或 LTS。具体任务和退出条件见路线图与 backlog。
