# Nexus 企业嵌入式研发与交付工作流

> 分析日期：2026-10-08。仓库证据基线：`7a203266082ad1f655b6686713b2b7950ba31ec6`。本文是维护与建设方案；“现状”描述已读取的代码和公开记录，“建议”描述待实施工作，“目标”描述需经过基线测量再调整的验收标准。本文不代表任何企业内部制度，也不宣称 Nexus 已达到安全认证或生产验证要求。

当前已确定首个建设方向为 **工业控制与设备联网**，团队约 **10 人**，目标平台包括 **STM32、GD32 等**，建设窗口为 **3–6 个月**。优先覆盖多 SKU、板卡 revision、生产烧录/校准/设备身份、长期维护和工厂/现场升级。具体芯片、板卡与业务尚未确定，计划先建立一个 STM32 参考配置，再验证一个 GD32 参考配置。第 3 个月目标是受控试点，第 6 个月目标是满足限定范围的双平台企业候选；两个目标都以硬件、验证与发布退出条件为前提。消费电子和安全相关场景用于检验架构扩展边界，安全关键资格作为未来单独 profile；首期不承诺安全认证或 LTS 支持年限。

## 1. 平台建设目标

Nexus 的企业价值应是：应用团队能重复构建一个已定义硬件配置的固件，在可解释的验证链上交付，并能追溯和恢复现场故障。统一 HAL 和 OSAL 只是这一能力的入口。工具链、硬件版本、配置、依赖、测试设备、签名、制造和更新策略一起构成交付平台。

第一阶段建议选择 **Native + 一块明确型号和板版的 STM32 板 + 一个 RTOS/裸机组合**，验证完整链路，再增加第二款产品或第二个 MCU 家族。为许多尚未验证的平台维护占位接口会消耗资源，也会把不确定性传递给产品团队。平台范围扩张应由真实产品和可维护的测试设备驱动。

企业交付必须能回答六个问题：

1. 这个二进制属于哪个产品、SKU、硬件版和配置？
2. 用哪些源码、依赖和工具链构建，是否可以重建？
3. 哪些需求、故障模型和真实硬件场景已经验证？
4. 谁批准发布，使用哪个签名密钥身份，发布包是否完整？
5. 哪些设备允许安装，失败时如何恢复，制造站如何识别？
6. 现场问题能否关联到构建、板卡、依赖和测试记录，并形成回归测试？

这六项是平台验收对象。测试数量、文档长度和抽象接口数量不能替代它们。

## 2. 当前工作流的可核实缺口

以下证据来自基线提交及 2026-10-08 的公开 GitHub 记录。工作流文件存在与工作流已经有效运行是两种状态。

| 现状证据 | 交付风险 | 建议优先级与动作 |
|---|---|---|
| 最近 5 次 CI 运行均为 `failure`，对应相同源码 SHA | 缺少当前可用的构建质量基线；每日运行重复消耗资源却未形成闭环 | P0：建立 CI 故障责任人，先恢复一个确定配置，再扩展矩阵 |
| `release.yml` 先创建 `draft: false` 的正式 Release，再运行依赖其完成的构建任务 | 构建失败时可能留下已公开、缺少制品的版本 | P0：验证、构建、打包和检查全部完成后，再发布完整 Release |
| 发布打包对缺失 `bin`、`lib` 使用 `\|\| true` | 包中可能只有 README 和 LICENSE，却仍上传成功 | P0：为 SDK 和板级固件分别定义必需制品；缺失即失败 |
| 发布构建步骤未见 `ctest`、板级验证证据和 SBOM/来源证明 | 版本标签与被测试的二进制之间缺少明确关系 | P0：发布使用被验证的同一制品；分阶段补齐发布证据 |
| `CI Status` 只判定 build-test 和 code-quality 的 `failure` | 文档失败、取消和异常跳过可能未被汇总门禁拒绝 | P0：建立每个事件类型的预期任务集合，缺失预期结果即失败 |
| `security.yml` 的 Safety 和 licensecheck 使用 `\|\| true` | 扫描报告生成不等于漏洞和许可证策略得到执行 | P1：区分扫描执行失败、发现问题和批准例外，执行可解释的策略 |
| 安全扫描主要覆盖 Python 依赖；没有从该文件看到 MCU SDK/RTOS 的完整物料清单 | C/C++ 和厂商固件依赖的漏洞、许可证、补丁来源可能遗漏 | P1：锁定全部依赖并对最终链接内容生成 SBOM |
| 部分 Actions 固定到版本标签，TruffleHog 使用 `@main` | CI 运行依赖可以漂移；复现与供应链审计变难 | P1：固定 Action 提交 SHA，以单独 PR 更新 |
| 主 PR 模板约 6.6 KB，重复要求代码、测试、文档、覆盖率等检查 | 容易形成机械勾选，也提高文档和低风险改动的成本 | P1：简化常规模板，按变更风险追加专项证据 |
| CONTRIBUTING 的 clone URL 和工作流名称与当前仓库不一致 | 新同事可能无法按文档开始工作 | P1：把入门命令作为可执行的清洁环境 smoke 检查 |
| releases API 当前返回空列表；公开 issue #1 报告 STM32F4 编译问题 | 尚无公开 Release 证据可用于认定长期发布质量 | P1：定义支持状态与首个验证版的明确范围 |

Issue #1 的维护者在 2026-01-27 回复 STM32F4 当时仍在开发。这个回复早于当前提交，因此只能证明历史沟通和成熟度表述曾存在差距；当前驱动能力必须以当前源码和板测证据重新判断。

支持状态建议分为：`experimental`、`validated`、`maintained`、`deprecated`。`validated` 必须带最后通过的构建 SHA、硬件版、工具链和测试记录；`maintained` 还必须有负责维护的人、验证频率和明确支持窗口。厂商 SDK 存在不能作为 Nexus 驱动已支持的证据。

## 3. 企业场景决定平台能力与过程深度

企业规模本身不能决定软件保证级别。一个小团队的医疗控制器可能需要比大型团队的消费电子配件更严谨的证据。下表是典型需求模型，实际范围需由产品、市场、失效后果和部署条件确认。

| 场景 | 典型约束 | Nexus 的优先能力 | 验证与交付要求 |
|---|---|---|---|
| 工业控制、仪表、能源设备 | 长生命周期；离线部署；确定性时序；电磁和电源异常；多批次替代料 | 清楚的 ISR/任务边界；有界分配；看门狗；持久化一致性；现场诊断；长期兼容接口 | 时序预算、温度和电源条件、总线异常、连续运行、断电恢复；现场服务升级和离线签名包 |
| 消费电子、联网传感器、家居设备 | 电池寿命；大规模 SKU；无线环境变化；网络攻击面；用户不能承担刷机恢复 | 电源管理；版本化协议；安全存储适配；可信更新；低成本遥测 | 唤醒和休眠、射频/网络故障、升级掉电、配置迁移、灰度发布、旧版本兼容 |
| 车载、医疗、铁路等含安全相关功能的产品 | 产品适用法规和保证级别；失效危害；工具和依赖的使用约束 | 可隔离安全子系统；静态资源模型；明确故障处理；需求与验证追溯 | 按适用标准建立生命周期、独立审查和证据；受控工具链、偏差管理、必要的 MC/DC 或其他覆盖要求；不能以一般 CI 宣称认证 |
| 多产品线和多地点团队 | 并行发布；多个板卡/RTOS；产品定制；供应商协作；支持旧型号 | 稳定核心；板级配置隔离；平台版本锁定；模块责任归属；兼容矩阵 | 产品与平台分别发布；选择代表配置；发布证据中心化；回补补丁和依赖更新计划 |
| 含 MCU 与嵌入式 Linux/高性能 SoC 的复杂设备 | 双端版本演进；启动顺序；跨核通信；多镜像升级 | MCU 端继续使用 Nexus；Linux 使用独立 BSP/系统构建；共享版本化通信契约 | IPC 模糊测试和故障注入；多镜像兼容范围；升级顺序和整体恢复；避免把 MCU HAL 扩展成通用 Linux 内核框架 |

对含安全相关功能的产品，应先区分安全控制链与非安全联网、UI、日志服务。Nexus 可先进入非安全域或经限定的组件使用范围。是否适用 ISO 26262、IEC 61508、IEC 62304 等标准，以及具体要求，应由产品保证计划确定；采用某个已认证 RTOS 不会自动认证整个应用。

### 首个工业产品链路的建议边界

建议以一个可被验证的工业采集/控制节点作为先导产品模型。模型用于确定平台任务，不能替代实际客户需求。产品将实时采集/控制与联网、日志和维护任务分开，联网断开、远端不可用或日志拥塞时，控制任务仍遵守产品定义的时限和故障行为。网络协议选择、Ethernet/蜂窝/Wi-Fi/RS-485 接入方式和实际 MCU 需在硬件确认后决定。

首期 SKU 可以共享应用核心，通过已评审的板级描述和产品配置选择传感器、通信方式、校准版本和资源限值，避免靠散布在业务代码中的 SKU 宏堆积差异。每个 SKU 至少定义：

- 采样/控制任务时限与最坏条件，通信或存储故障时的本地行为。
- 工业协议/联网协议契约及版本，输入边界、重连和拥塞策略。
- 非易失存储布局、校准数据身份、断电一致性和维护写入策略。
- 看门狗、复位原因、现场诊断读取方式和明确的恢复流程。
- 制造工站烧录/校准/设备身份步骤与允许的板卡 revision。
- 工厂、现场服务和远程升级权限，维护窗口、离线设备与长期兼容策略。

验收应至少演练：通信线断开后控制行为符合要求；工站不会向错误板版烧录；校准数据在重刷应用后符合保留/重建政策；每个存储和升级关键步骤掉电后能恢复到定义状态；确切旧版本在清洁环境可重建并交付维护修复。量产环境、EMC、温度和寿命验证由具体产品计划补齐。

### 大团队实际需要管理的三种变化

**软件变化**包括接口、调度、数据格式和依赖版本；**硬件变化**包括晶振、Flash、电源、传感器和板版；**部署变化**包括工厂烧录、区域配置、运营商网络和现场安装方式。三者需要独立身份和兼容约束。一句“STM32F4 支持”不足以表达这些变化。

典型替代料变更流程是：硬件提出变更单，BSP 标记受影响板版和驱动能力，平台验证电气与时序差异，产品锁定新配置，制造站检查兼容清单，现场更新禁止向旧板推送不兼容固件。硬件变更单与软件 PR 可以不同工具管理，但必须在发布记录中互相引用。

## 4. 平台与产品的责任边界

建议先在当前仓库维护核心和参考板，不立即拆成大量仓库。产品数量和权限边界增长后，再使用被锁定的版本清单或制品引用组成工作区。清单必须能表达确切提交，不依赖浮动的 `main`。

| 责任域 | 包含 | 不应承担 |
|---|---|---|
| 平台核心 | HAL/OSAL 契约、共用组件、配置和构建规范、可移植测试设施 | 客户业务规则、工厂私钥、每个产品的全部发布审批 |
| SoC/板级支持 | 启动、链接、时钟、中断、引脚和驱动适配、硬件能力与勘误 | 把业务配置写死在驱动；用成功返回掩盖未实现功能 |
| 产品应用 | 产品需求、调度和资源预算、协议、配置模式、制造与 OTA 策略 | 任意修改平台内部后不回传；绕过 HAL 的未记录厂商调用 |
| 交付工具 | 固定工具链、CI、测试设备编排、制品与证据存储 | 在普通 PR CI 中持有生产签名密钥 |
| 企业集成 | 身份权限、审批记录、产品资产/工厂/设备队列对接 | 把特定云厂商账号结构嵌进核心运行时 |

平台 API 的兼容性应分别管理：源码兼容、二进制兼容、持久化格式兼容、线协议兼容、硬件兼容。嵌入式项目通常整体静态链接，未必承诺跨编译器 ABI；真正的承诺应写明，避免语义化版本号产生超出实际支持范围的预期。

### 产品配置清单的建议内容

产品配置是可评审和可版本化的源输入。下例只是建议数据模型，当前不表示仓库已有该解析器：

```yaml
product: industrial-sensor
sku: sensor-rs485
hardware:
  board: reference-stm32f4
  revision: B
platform:
  nexus_commit: "<full-commit-sha>"
  os: freertos
  os_commit: "<full-commit-sha>"
build:
  profile: production
  toolchain_digest: "<immutable-toolchain-identity>"
  config_fragment: configs/sensor-rs485-prod.conf
compatibility:
  bootloader_min: "<tested-version>"
  config_schema: 2
  protocol_schema: 1
budgets:
  flash_bytes: "<measured-product-limit>"
  ram_bytes: "<measured-product-limit>"
  critical_task_deadline_us: "<product-requirement>"
verification:
  required_hil_suites: [boot, uart, power_loss]
```

清单中不存储设备凭据、生产签名密钥或生产秘密。生成配置和编译产物属于各自构建目录，不能让一个产品生成的 `.config` 覆盖另一个产品的输入。

## 5. 从需求到现场的证据链

建议用稳定 ID 和链接贯通已有工具，保持需求和结论各自只有一个权威来源。初期可用 GitHub Issues、仓库 ADR 和 CI 制品完成，不需要先采购完整 ALM 平台。

```text
需求/缺陷/硬件变更
    ↓ 风险、验收条件、受影响产品
ADR/接口契约/资源和故障预算
    ↓ 需求 ID 与设计决策
短分支 → PR → 自动检查 + 有责任人的评审
    ↓ 被测试的源码 SHA、配置与二进制哈希
SIL/目标编译/必要 HIL/产品资格验证
    ↓ 验证记录与未解决风险
候选发布 → 制品检查 → 受控签名 → 完整发布包
    ↓ 适用硬件、版本兼容、回退约束
制造/服务升级/分批 OTA
    ↓ 设备版本与安装结果
现场诊断 → 缺陷复现 → 新增回归场景 → 维护发布
```

SIL 指在主机或仿真环境验证软件逻辑；HIL 指真实目标硬件连接测试设备。Native 模拟不能验证电气行为、DMA 缓存一致性、真实中断和硬件时序，也不能替代产品环境资格测试。

| 阶段 | 必要输入 | 可评审输出 | 退出条件 |
|---|---|---|---|
| 需求整理 | 使用场景、受影响产品、失败后果 | 需求 ID、可测验收、风险级别、资源或时间限制 | 责任人接受需求；验收没有“高性能”“稳定”之类未量化表述 |
| 设计 | 接口和约束、已有实现、故障模型 | 必要的 ADR、接口契约、迁移和验证方案 | 高影响选择经过相关维护者评审；常规局部实现不强制 ADR |
| 实现 | 已接受需求、明确配置 | 小范围 PR、实现与回归证据、文档变化 | 适用自动门禁通过；有维护者评审；例外有责任人与到期日 |
| 集成验证 | 确切 SHA 和候选制品 | SIL/HIL 报告、性能资源预算、配置和板卡身份 | 预期验证全部完成，失败已处理；没有用 skipped 替代硬件通过 |
| 发布 | 通过验证的不可变制品 | 完整发布包、签名、兼容清单、已知问题和支持窗口 | 必需制品存在，哈希与验证记录一致，签名及恢复路径验证 |
| 制造与部署 | 产品/SKU/硬件身份、发布包 | 烧录/校准/测试/设备身份记录、部署结果 | 烧录后验证、功能检查与生产配置检查通过 |
| 现场闭环 | 固件身份、崩溃/日志/环境、设备和批次信息 | 缺陷、根因、修复/规避、回归测试和服务措施 | 受影响版本和设备范围确定；修复被重新验证并交付 |

### 需求和 ADR 的最小结构

常规需求包含场景、验收、风险、兼容影响、产品配置和负责人即可。涉及调度方式、公开 API、持久化格式、启动更新、加密、依赖或仓库边界的选择应建立 ADR：问题、约束、候选方案、选择理由、验证方式、迁移策略与复审触发条件。ADR 记录决定和后果，不记录所有代码细节。

需求到测试的关联必须校验“测试实际执行并通过”，不是只检查存在测试函数名。一个缺陷可以关联多个测试，一个测试可以覆盖多个需求；需要保留未覆盖清单并解释原因。

## 6. 按变更风险配置流程

推荐使用轻量风险分级决定评审和验证，而不是让每个 PR 填满同一张大表。

| 级别 | 示例 | 评审与证据建议 |
|---|---|---|
| R0 | 文档措辞、纯格式变化 | 文档/格式检查；一名维护者，符合团队策略时可授权快速合并；不强制新增单测 |
| R1 | 局部业务修复、明确的低影响工具改动 | 一名相关维护者；受影响测试和必要构建；记录兼容影响 |
| R2 | 驱动、DMA/ISR、调度、公共 API、存储格式、工具链或依赖变化 | 模块维护者与相关验证负责人；契约/故障/集成测试；触达硬件行为时 HIL；必要 ADR |
| R3 | Bootloader、更新恢复、生产密钥路径、安全相关控制、具有严重现场失效后果的变化 | 独立于实现者的专项评审和发布判断；安全/保证计划指定验证；必要的故障注入、迁移和恢复证据 |

风险级别需结合产品配置。例如同一个 UART 改动用于调试串口和用于安全相关控制总线时，所需产品证据不同。标签不能让自动化替代工程判断。

PR 最小内容建议为：**问题与触发条件、最终变化、影响配置/接口、验证结果、风险/迁移**。将构建、格式、扫描和测试结果自动引用进 PR，不让作者重复抄写一份可能过期的报告。发布与安全相关变更使用专项模板。

完成定义包含“受影响验证已通过”和“故障处理得到验证”；不能要求所有 PR 在所有未维护平台都通过，也不能用单一覆盖率阈值阻断无运行行为的编辑。新增运行行为需要有价值的测试，测试应验证需求和故障，不仅镜像实现。

## 7. 本地开发、CI 与测试设备工作流

### 本地与 CI 共用入口

建议保留 CMake/CTest 为底层权威接口，Python 仅编排确定的命令和元数据。统一任务入口应支持：检查环境、选择明确 profile、配置、构建、测试、打包和生成证据。不得一边使用 preset，一边由脚本偷偷重写另一套平台配置。

工具链在容器或可下载包中固定版本与哈希。Native 开发保留宿主机方式，避免所有人都必须运行容器。生产构建要求清洁输入、固定 locale/time/path 处理与依赖来源；缓存加速不应影响配置和工具链身份的校验。

### 四层验证节奏

以下时间是初始建设目标，需在恢复基线后测量并调整，不代表当前表现。

| 层级 | 触发 | 内容 | 初始反馈目标 |
|---|---|---|---|
| L0 | 开发者本地/提交前 | 受影响格式、静态检查、快速单测、入门示例构建 | p95 不超过 5 分钟；允许按模块运行 |
| L1 | PR | Native 测试、适用 sanitizer、受影响目标编译、接口/配置检查、必要扫描 | p95 不超过 15 分钟；评审看到确定结果 |
| L2 | 主干和 nightly | 扩展配置矩阵、驱动契约、压力/模糊测试、真实板 smoke/必要 HIL | 首先保证结论可靠，再控制成本和排队 |
| L3 | 候选发布/产品里程碑 | 精确产品配置、长稳、资源/时序/功耗、升级和断电恢复、必要资格验证 | 按产品风险制定时限，全部必需证据完成后释放 |

变更影响选择需覆盖 HAL/OSAL 公共头、Kconfig、构建脚本、工具链、板级文件和依赖清单。未知变更默认扩大验证。PR 可做选择性验证，nightly 和 Release 保留已维护配置的全面验证以发现选择器遗漏。未维护组合必须显示状态，不能只用“跳过”隐藏。

### CI 汇总门禁真值表

每个事件先确定任务集合，再校验实际结果。任务的完成状态与被选中是否应该执行是两个字段。

| 是否要求执行 | 实际结果 | 门禁结论 |
|---|---|---|
| 是 | success | 通过该项 |
| 是 | failure / cancelled / timed_out / action_required | 失败 |
| 是 | skipped / missing / 无制品 | 失败，报告为什么缺失 |
| 否，选择器已给出理由 | skipped | 允许，保留理由 |
| 否 | failure | 标为失败并处理；至少不能作为可用发布证据 |

文档改动可以不运行驱动 HIL，但文档构建是该事件的预期任务；代码改动中出现预期测试取消也不应变成通过。工作流显式 `workflow_dispatch` 应能运行指定配置，不能因缺少路径匹配而无声跳过。

### HIL 实验室

每台测试设备登记设备 ID、板版、SoC/Flash 型号、连接端口、夹具、测量设备版本、固件哈希和最后校准/维护状态。测试任务获得独占租约，完成后恢复明确状态。失败保留 UART 日志、调试器输出、复位原因及需要的波形/功耗数据。

需要区分软件失败、夹具故障、测试超时和环境异常。夹具故障可以隔离设备并重测，不能无限自动重试把间歇性软件失败抹成绿色。隔离测试必须有缺陷、责任人和到期日；被隔离的发布必需验证不能自动视为通过。

初期推荐一套可远程控制电源、调试器和串口的参考板夹具；先验证启动、GPIO、UART、SPI 和恢复，再扩充总线/传感器。ISR 延迟、DMA 压力、供电波动、通信断连、Flash 断电和 watchdog 复位应按产品风险增加，不在没有设备的情况下宣称完成。

## 8. 发布设计：平台、板支持包和产品分别交付

### 发布类型

| 类型 | 内容 | 版本承诺 |
|---|---|---|
| 平台 SDK | 公共接口、核心源码或库、固定依赖清单、构建工具和示例 | 明确源码/二进制兼容范围与迁移指引 |
| 板支持包 | 启动、链接、硬件描述、驱动适配、勘误和板测证据 | 指定板版、工具链、Nexus 范围和受维护外设 |
| 产品固件 | Bootloader/应用/必要其他镜像、产品配置、兼容与部署规则 | 指定 SKU/硬件/配置格式/协议范围；升级和恢复规则 |

平台语义化版本不能代替产品固件身份。产品 Release 可以锁定某个平台提交并回补修复；回补 PR 应关联原始修复和每个维护分支的验证。破坏性接口变化有迁移期，旧产品不应被强迫立刻追随平台主干。

建议主干保持可集成，使用短分支；只为实际支持的产品或长期支持版本创建维护分支。避免同时要求所有工作先进入 `develop` 再进入 `main`，除非确有双集成线需求。长期产品分支应有终止日期与回补策略，避免无界维护。

### 原子化发布顺序

1. 从确切提交、固定工具链和产品配置构建候选制品；版本输入严格校验，避免直接把未经验证的 dispatch 字段拼进 shell。
2. 对候选制品进行预期 SIL/HIL/产品验证，记录二进制哈希；若验证环境需重新构建，先证明重建制品一致。
3. 按发布类型检查必需文件、非空体积、目标架构、链接映射、依赖和许可证清单，生成哈希与来源证明。
4. 通过风险与发布判断，将同一候选制品送往受控签名流程；签名只改变约定的签名封装，不替换已验证代码。
5. 在发布前检查签名、包内容和适用硬件规则；需要设备验证时测试最终签名包。
6. 原子地公开完整包和证据链接；GitHub 可先建私有草稿并最后转为公开，或全部就绪后创建正式 Release。
7. 产品按部署计划推进，失败暂停和恢复；完整留存发布决策和已知问题。

如果使用标签作为工作流触发器，标签代表候选输入，而不是“正式发布已经完成”。`-rc` 等候选版本应正确标记 prerelease。发布任务失败时不出现已公开的空版本，不重新使用相同版本号指向另一套内容。

### 最小发布包

平台 SDK 和产品固件需要不同的必需文件列表。对产品固件，建议包含：

- 最终签名镜像和必要的 boot/应用/辅助镜像，适用的 ELF、MAP 和调试符号存入有权限的证据库。
- 发布清单：产品/SKU、硬件范围、源码 SHA、工具链身份、配置哈希、依赖锁定、每个制品哈希。
- SBOM、许可证与版权材料、构建来源证明、签名密钥身份和算法信息。
- SIL/HIL/产品验证记录、异常与已批准风险、变更日志、支持窗口。
- Bootloader/协议/配置兼容表、升级前提、制造/部署说明和恢复约束。

证据库保留期依据产品支持期和适用义务确定，不依赖 GitHub 临时 artifact 的默认存留天数。产物、源码和依赖的备份应支持旧产品在上游停止服务后重建。含用户/设备敏感信息的诊断制品需要访问控制和适用的删除策略。

## 9. 软件供应链、安全与长期维护

依赖来源包括 RTOS、CMSIS/厂商 SDK、加密库、bootloader、协议栈、编译器、构建镜像、Python 工具和 CI Actions。全部纳入清单和更新策略。对 vendored 源码记录上游版本、提交、许可证、补丁及责任人；定制差异可追溯，升级时能重放或删除补丁。

生成 SBOM 需要区分“仓库中存在”和“产品实际链接”。同时保留源码依赖清单与最终制品依赖清单。某组件的漏洞是否影响产品，应结合版本、配置、可达性、攻击条件和部署环境判断。初期由责任人记录适用性，规模增长后可用 VEX 表达判断。

扫描流程必须区别：扫描器执行失败、发现问题、没有发现问题。不能把 `|| true` 的结果直接当绿色门禁。建议阻断新引入且适用于产品的高风险漏洞和禁止许可证；旧问题按受影响版本和修复期限管理。批准例外包含理由、补偿措施、负责人和到期日期。

生产签名应独立于普通 CI 和 HIL runner。使用受控签名服务或 HSM/KMS，最小权限、日志和密钥轮换；开发/test key 明确标识且被生产设备拒绝。PR 来自不可信代码时不能访问签名权限或生产设备凭据。需要上传的源码、日志和符号也应按权限过滤。

安全维护需建立私密漏洞接收渠道和公开披露规则，内部缺陷关联受影响平台/产品/设备范围。发布补丁应覆盖真实维护分支，不仅修复最新主干。渠道配置、权限设置和外部沟通属于后续实施任务，本文没有创建或发送任何外部消息。

## 10. 制造、校准和设备生命周期

制造工作流不应只有“刷入最新固件”。建议由签名发布包驱动制造，工站使用固定工具和脚本并校验版本。设备身份、校准数据、出厂配置与应用镜像分开管理。

制造顺序建议为：核验硬件/工单 → 烧录允许的 boot 与应用 → 注入唯一设备身份和凭据 → 校准与功能测试 → 校验生产配置/调试策略 → 记录出厂结果。每一步有明确失败处理，避免重跑脚本重复消耗计数器、锁死 Flash 或覆盖唯一身份。

设备私钥在安全元件生成或通过受控站点注入，选择由硬件能力和威胁模型决定；不能把全产品共享私钥放进普通应用镜像。工站权限和固件签名权限分别控制。制造日志保存密钥标识和成功状态，禁止记录私钥明文。

调试端口的生产策略、返修解锁、擦除、凭据吊销和报废是同一生命周期的一部分。关闭调试前验证返修路径和芯片勘误，不要把一次不可逆硬件设置当成通用框架默认行为。平台提供适配能力，产品决定政策，制造执行并记录。

硬件替代料或工站脚本变更应触发适用的重新资格验证。设备出厂记录关联：序列号或隐私友好的设备 ID、产品/SKU、硬件和批次、固件/boot 版本、制品哈希、校准版本、工站版本、测试和返工结果。

## 11. OTA、离线升级与现场闭环

### 升级是持久化状态机

平台应提供 boot/update/storage 的可测试契约，产品实现网络、授权、设备分组和安装时机。应用层收到包不等于设备可以安全重启。工业设备可能必须在维护窗口安装；控制器可能需要进入已定义的安全状态；低电量设备可能应延后。

升级流程建议为：检查包身份与目标硬件 → 完整下载/校验 → 保留恢复镜像或替代恢复手段 → 写入候选状态 → 安装 → 验证启动/关键功能 → 确认 → 上报。每个持久化步骤都有掉电和重复执行策略。双槽只是可选实现，Flash 不足的设备需要经验证的其他恢复机制。

Bootloader 的镜像回退与安全防降级必须区分。运行失败时需要回到允许的已知可用镜像，安全计数器却可能禁止旧版本；版本策略不能在验证前把唯一恢复镜像变成不允许安装。具体确认与计数器更新顺序应按所选 bootloader 能力设计并测试。

配置模式和校准数据与固件一起管理兼容。先设计旧/新镜像对持久化格式的读取范围，再设计迁移。不可逆迁移需要明确恢复方案；“固件可回退”不代表“数据可回退”。

### 分批部署

建议从内部设备、受控试点到分批量产设备推进。比例和停留时间由风险、设备数和观测能力决定，不预设所有产品都适合 1%/10%/100%。每一批都限定 SKU/硬件/boot/配置范围，并定义停止条件：启动失败、异常复位、升级失败、核心功能故障、资源或功耗恶化。

设备长期离线时需要重新判断升级资格和包期限。离线服务升级也使用同一签名和兼容规则，不能成为跳过校验的旁路。发布撤回、暂停安装、包吊销与设备端允许回退策略应有可执行手册。

### 现场问题处理

现场诊断至少能提取固件身份、复位原因、关键错误计数和有界崩溃记录；复杂产品可增加 trace。日志设计要考虑 Flash 寿命、实时性能、敏感信息和离线读取，而不默认上传所有数据。

事故流程是：确定影响和临时规避 → 暂停必要部署 → 保存证据 → 用确切版本与板版复现 → 根因与修复 → 回归验证 → 补丁/服务措施 → 更新诊断和测试。复盘不以谁写错代码为终点，应检查接口契约、门禁、硬件假设和发布规则怎样容许问题进入现场。

## 12. 角色、治理和工作节奏

角色是职责，不要求每个角色招聘一个人。小团队可以兼任，但高风险审批和生产签名尽可能与实现分离。

| 角色 | 决策/责任 | 必须形成的记录 |
|---|---|---|
| 平台负责人 | 核心接口、维护范围、路线图和破坏性变更 | ADR、支持矩阵、兼容和弃用计划 |
| 模块/板维护者 | 驱动和组件质量、依赖补丁、审查与问题处理 | 契约、模块测试、已知限制和硬件验证 |
| 产品负责人/产品工程师 | 需求优先级、SKU 和产品验收、现场价值 | 产品配置、验收和发布/支持范围 |
| 测试/验证负责人 | 验证策略、夹具、证据真实性与产品质量风险 | SIL/HIL 结果、隔离记录、验证空白 |
| 安全/软件保证负责人 | 漏洞、密钥与高风险保证要求 | 威胁模型、适用性判断、偏差/例外、保证证据 |
| 发布负责人 | 候选与正式制品一致、包完整、发布和恢复判断 | 发布清单、签名与验收、已知问题 |
| 制造/服务负责人 | 工站、校准、身份和现场升级/返修 | 出厂和服务记录、工站验证、现场缺陷 |

### 10 人团队的建议分工

以约 10 人持续投入为容量假设，采用六个协作责任域；不是六个独立团队，也不要求额外招聘产品、制造和安全专职岗位。相关职责由以下成员兼任，产品或硬件对接人按实际组织确定。

| 人员安排 | 数量 | 主要产出 |
|---|---|---|
| 平台/技术负责人 | 1 | 工业场景范围、架构/ADR、验收优先级、接口与发布风险决策；兼任安全和制造接口协调 |
| 核心 HAL/OSAL 工程师 | 2 | 生命周期、ISR/任务/超时/资源契约、核心组件、Native 与平台契约测试 |
| BSP 工程师 | 2 | STM32/GD32 启动、链接、时钟与驱动；首先完成 STM32 链路，同时评估 GD32 差异，随后收敛第二平台 |
| 工业产品/协议工程师 | 2 | 采集/控制先导应用、产品/SKU 配置、工业通信与联网、诊断和制造/升级业务策略 |
| QA/HIL 工程师 | 2 | 验证计划、板卡夹具、契约/故障/断电/长稳测试、制造与现场演练、候选证据检查 |
| 构建/发布工程师 | 1 | 固定工具链、CI、依赖清单、制品完整性、签名流程对接和发布证据归档 |
| **合计** | **10** | **一个主干、一个工业先导链路、两个逐步验证的 MCU 家族** |

首期不同时开展多个 RTOS、多个工业协议栈和大量芯片移植。GD32 与 STM32 的接口相似性不能替代时钟、Flash、DMA、IRQ 和厂商 SDK 的独立验证。每个关键域保留第二位可审查/接手的人，构建/发布由负责人和 QA 提供备份；高风险实现者不独自批准自己的发布。

CODEOWNERS 是评审路由，不是完整组织架构。所有权规则应覆盖 HAL、OSAL、板级、配置构建、测试、Bootloader/加密及工作流。分支保护需要在仓库权限允许时配置：禁止直接推送受保护分支、要求适用门禁和评审、记录例外。本文没有修改远端权限。

建议每周完成故障和风险分流，每两周或每个产品节奏进行小版本演示/集成，每月审阅支持矩阵、依赖和技术债；高影响 ADR 按需评审，不把所有开发等待固定会议。nightly 的持续红色在下一次分流前已有责任人；严重问题按团队响应值班处理。

积压项至少带类型、风险、模块、受影响产品和里程碑。架构债、构建故障、硬件验证空白与功能都进入同一优先级讨论。优先级参考用户/现场影响、发生概率、验证不确定性和修复成本；没有现场信息时记录假设，不能编造损失数字。

### 三种团队规模

| 团队条件 | 建议流程 | 何时增加控制 |
|---|---|---|
| 1–5 人、一个参考产品 | 一个仓库；简短 issue/PR；少量 ADR；Native 和一套板测；人工检查完整发布包 | 出现生产签名、量产、严重失效或第二条产品线时增加专门职责与发布记录 |
| 6–30 人、多板或多产品 | 模块维护者/CODEOWNERS；产品锁定清单；风险分级；维护分支；共享 HIL 设备与证据库 | 多团队争用设备、依赖和接口；出现维护窗口冲突或长期支持承诺时扩展 |
| 30 人以上、多地点或外部供应商 | 平台/产品职责独立；签名服务；实验室设备调度；可检索证据与审计；按合同划分权限 | 工具集成自动同步状态；供应商交付物和生产资产纳入清单；保证级别决定独立性 |

以上人数仅作组织示例，不是合规门槛。复杂度和失效后果比人数更重要。工具可用 GitHub Projects 或与现有企业系统链接，初期无需同时引入 Jira、GitLab、Jenkins、商业 ALM 和全套服务。

AI 辅助开发可用于源码检索、初稿、契约审查和测试场景建议。生成代码遵守相同 PR/验证规则，禁止把生产秘密输入外部模型；安全相关保证结论、生产签名和发布授权仍由被指定的责任人承担。AI 提出的事实必须指向源码、测试或可核实外部来源。

## 13. 可用于决策的指标

先恢复可运行基线，连续观察 2–4 周，再固定目标。按配置和产品分组报告 p50/p95、分母和窗口，避免把多平台成功与失败平均成一个绿色数值。指标用于改善系统，不用于简单排名个人。

| 指标 | 定义 | 初始目标/解释 |
|---|---|---|
| 清洁构建成功率 | 固定输入在清洁环境完整构建成功次数 / 同配置有效次数 | 参考配置先达到连续 10 次成功；网络和实验室异常单独报告，不从失败事实中抹除 |
| PR 自动反馈延迟 | 提交到适用自动门禁结果，含排队 | L1 p95 ≤15 分钟，依据机器和矩阵成本调整 |
| 主干稳定性 | 受维护配置完整门禁 success 次数 / 预期运行次数 | 初始目标 ≥95%；失败恢复 p95 ≤1 个工作日；发布必需检查仍要求全部成功 |
| 测试不稳定率 | 相同源码/输入无软件变化时非确定结果次数 / 执行次数 | 初始目标 <1%；每个隔离项有责任人和期限 |
| 发布完整性 | 包和证据清单完整的正式版本 / 正式版本 | 100%；不允许缺失制品的公开正式版本 |
| 高风险验收追溯 | 有实际通过验证与记录的高风险验收项 / 应验证验收项 | 发布前 100%；未通过项按保证计划处理，不能用“测试存在”计数 |
| 现场逃逸 | 现场确认的平台相关缺陷，按严重度、版本、设备数/运行时计 | 首先建立分母和归因；不能与 issue 总数混用 |
| 升级成功与恢复率 | 合格设备中确认安装成功数，以及失败设备中恢复数 | 按批次、硬件和连接条件报告；目标由产品部署要求确定 |
| 资源/时序预算 | Flash/RAM/栈/执行与中断延迟相对产品限值 | 发布配置无超预算；保留余量和测量方法 |
| 安全维护周期 | 确认适用漏洞到可交付修复时间，按严重度 | 在制定响应计划后设置目标；报告超期和批准例外 |
| 平台复用收益 | 新产品从清洁环境到有效板上示例、到首个业务验证的时间 | 先量基线，再与相近产品比较，避免用代码共享比例代替成本收益 |

覆盖率、测试个数和构建矩阵规模只是辅助指标。可以为高风险模块追踪条件/分支覆盖，对硬件故障、实时性和加密安全仍需要其他证据。定义共同的性能基准板、工具链、功耗设备和测试条件，跨条件数据不直接比较。

## 14. 分阶段实施与退出标准

以下路线按约 10 人、3–6 个月规划，时间从人员实际投入、可用板卡和调试设备到位后计算。芯片/板版、Flash 空间、协议与产品风险仍影响范围；遇到前置条件不足时缩小目标配置或调整日期，不削弱退出标准。进度首先由一条可运行、可诊断、可恢复的工业链路驱动，第二平台通过相同契约和产品验收确认复用。

| 阶段/目标窗口 | 建设事项 | 可验证退出条件 |
|---|---|---|
| A：第 1 个月，可信基线 | 恢复 Native/STM32 明确配置；修复发布先公开后构建；拒绝缺失制品；门禁正确汇总；更正入门和支持状态；盘点 GD32 SDK 与硬件差异 | 清洁环境按文档重复运行；参考配置连续成功；故意构建失败不产生公开正式 Release；预期任务取消/缺失会失败；已选参考硬件与必需能力清单 |
| B：第 2 个月，首条工业链路 | 产品/SKU 配置、需求/ADR/PR最小模板、一套 STM32 HIL、采集/控制与通信故障隔离、候选发布包 | 同一源码/配置对应二进制哈希和板测记录；启动/通信/存储相关必需场景通过；时序和资源预算可测；每个已知限制有结论 |
| C：第 3 个月，受控试点 | 限定硬件/SKU/设备范围；制造烧录与校准、设备身份、工厂/现场升级、签名候选与诊断；制定停止和恢复手册 | 最终候选制品与证据一致；制造和维护演练通过；选定恢复机制的掉电场景实测通过；受控设备上验证实际业务；不存在未处置的高影响风险；不据此认定量产或 LTS |
| D：第 4–6 个月，双平台企业候选 | 增加 GD32 参考板；核心契约两平台验证；多 SKU 与板版兼容、SBOM/来源证明、受控签名、维护分支、长稳与更新恢复；按选择的真实业务补齐工业协议与联网能力 | STM32/GD32 各至少一个明确板版和产品配置通过必需 SIL/HIL；同一工业业务可复用核心；制造/现场升级/回补补丁/返修有实测证据；正式包完整可追溯；资源与时序满足产品预算 |
| E：第 6 个月后，按产品扩展 | 根据需求扩展更多芯片/协议/产品和支持期限；安全关键单独 profile；必要时建立高保证或多地点治理 | 每次扩展有维护容量、硬件验证和退出条件；适用资格通过约定评估后才声明；LTS 年限有正式支持计划后才承诺 |

**3 个月受控试点成立的条件**是：目标板和夹具及时可用，业务限定为一个工业先导链路，升级恢复方案与 Flash/boot 能力匹配，发布及现场诊断可实际操作。条件未满足时保留开发候选，不把未上板的模拟结果描述为试点就绪。

**6 个月双平台企业候选成立的条件**是：第二平台硬件和厂商依赖可用，两个平台的必需能力得到真实验证，支持矩阵明确到芯片/板版/外设/RTOS组合，多 SKU 制造和服务策略完成演练。候选的“企业”范围指受控交付、追溯和维护机制；具体产品的量产资格、环境可靠性和法定要求仍由该产品计划验收。日历到期本身不能提升支持状态。

第一批可执行积压项建议：

1. **CI-001**：构建目录级配置隔离与清洁环境 smoke，阻断源树 `.config` 污染产品选择。
2. **REL-001**：候选构建/验证先于正式发布，校验 SDK/固件必需制品，并演练发布失败。
3. **CI-002**：门禁任务集合和结果真值表，保证 failure/cancelled/异常 skipped 不会通过。
4. **DEV-001**：缩短常规 PR 模板，增加风险/硬件/持久化与兼容影响字段，修正 CONTRIBUTING。
5. **BSP-001**：为一块参考板记录板版、工具链、已验证外设、限制和维护人，建立基本 HIL。
6. **SUP-001**：盘点 C/RTOS/厂商 SDK/工具/Actions，固定版本并建立受控更新和例外记录。
7. **PROD-001**：产品/SKU/硬件/配置/固件身份与发布清单，明确制造、升级和数据兼容规则。
8. **OPS-001**：以参考产品演练断电升级、崩溃诊断、回补发布和返修，结果回流为测试与手册。

这些是本地规划项，没有在远端创建 issue。实施时每项应缩小为可独立评审的 PR，避免以“全面重构”一次替换所有接口、驱动和流程。

### 可借鉴的公开机制

以下是公开项目的实际机制，不据此推断任何公司内部开发流程。外部文档链接指向读取时的 `main`；正式引入依赖前应进一步锁定提交和适用版本。

- [Zephyr west manifest](https://github.com/zephyrproject-rtos/zephyr/blob/main/doc/develop/west/manifest.rst)：用一个版本化清单表示多个仓库的确切 revision，适用于多产品工作区和依赖锁定。
- [Zephyr CI test-plan selector](https://github.com/zephyrproject-rtos/zephyr/blob/main/doc/develop/test/ci_test_plan.rst)：按板、SoC、驱动、配置、公共头和维护区域选择测试，说明大矩阵可以用显式影响模型控制成本；Nexus 应先实现简单可靠的选择规则。
- [FreeRTOS manifest](https://github.com/FreeRTOS/FreeRTOS/blob/main/manifest.yml)：公开记录 RTOS、协议、安全组件与依赖 revision。其示例含不同形式的 revision，Nexus 的正式发布应解析并保存最终完整提交/哈希。
- [MCUboot 设计](https://github.com/mcu-tools/mcuboot/blob/main/docs/design.md)：公开描述镜像格式、test/permanent/revert、确认与安全计数器，适合参考更新状态机；选择功能仍需验证目标 Flash 和 boot port，不能假定任意配置都支持同样恢复能力。
