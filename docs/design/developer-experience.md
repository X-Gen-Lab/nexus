# Developer experience and provider iteration

This iteration keeps the static factory and shared polymorphic interfaces while
reducing unnecessary product and maintenance work. The
[75-task execution ledger](developer-experience-execution.csv) is the task-status
authority; its [readable view](../status/ledgers/developer-experience.md) preserves
the same fields: W1–W9 contain 63 software work items, I-01–I-06 track integration, and
H1–H6 require connected equipment. Implementation, software execution and physical
execution are separate columns. A software mechanism does not close a physical
exit condition.

## Boundaries that stay explicit

The current [architecture diagram](../explanation/platform-architecture.md) still
applies. One product TOML becomes immutable typed IR and exact static instances;
CMake selects sources. Factory getters return existing readonly faces. Products
own execution, storage, private PCB and recovery policy outside this repository.
A friendlier command does not create a second configuration or build authority.

| Work package | Delivered mechanism and source of truth | Exit evidence |
| --- | --- | --- |
| W1: application entry | External versioned templates and `dev.py create`; SDK maintenance remains separate | Created application actually resolves, builds and runs; template and actual SDK identities remain distinct |
| W2: configuration | Board-first bindings, validated profiles, human explanation, effective diff and editor schema | Normal rejection and immutable resolved output remain authoritative |
| W3: provider boundaries | Family resolution and typed construction; common arbitration and atomic publication | Equivalent configurations retain generated bytes; moved source remains selected by CMake and SDK |
| W4: support selection | Existing Board/SoC facts, provider modes, derived matrix and explicit unknowns | Exact route, backend, mode, memory and evidence match; no second support-status database |
| W5: lifecycle use | External main-loop, exclusive-task and shared-owner recipes; optional copied-fact diagnostics | Borrow, backpressure, cancellation, drain and observer-join behavior actually executes |
| W6: resource cost | Actual linked variants, existing image reports and selected physical measurement plans | Equivalent-cost rules distinguish measured deltas from unexecuted timing |
| W7: official reuse | Locked vendor source and one bounded actual HAL/SPL evaluation | Semantics, linked costs and maintenance scope justify one production implementation |
| W8: execution efficiency | Existing process receipts, focused development and complete final gates | Timings preserve unknowns and failure; any test deletion preserves independent coverage |
| W9: external integration | Actual examples applications, source lock and public SDK consumption | Platform P and examples E are fixed in the final delivery association |

## Source ownership and migration

The H743 DMA2D component lives at
`components/soc/stm32/stm32h743_frame_dma2d`. Its public include
`nexus/components/frame_dma2d.h` and CMake target stay stable. This is a private
source ownership correction, not new multimedia or hardware support. Historical
records keep the paths belonging to their recorded revisions.

`explain` now prints a human summary by default; automation must use `--json`.
The optional owner observation gains admission facts and changes its public
sidecar layout, so source consumers recompile. New helpers do not add mandatory
state to every provider, allocate a global registry or release borrowed storage.
The [product workflow](../guides/developer-workflow.md) documents these changes.

Official library reuse is evaluated per exact operation. A library name alone
does not determine timing or ownership. The F4 HAL reference is finite USART1 TX
with DMA2 Stream7; it is not a production backend or a migration of every mode.
For HAL v1.8.5, DMA transfer-error IRQ cleanup uses a bounded
`SystemCoreClock / 9600` enable-bit loop. Tick waits occur in separate DMA Init,
Abort and PollForTransfer paths. Do not describe every normal finite TX or
interrupt-driven abort as a `HAL_GetTick` wait. The
[official provider contract](official-stm32-provider.md) retains callback,
deadline, single-owner and full-drain obligations.

The current decision retains the single production LL/provider engine and GD32
SPL operation reuse. Actual HAL software behavior, current production ELF costs
and non-equivalent ARM handle layouts are recorded separately. The reference
does not implement complete NVIC preemption/vector withdrawal, IRQ wake,
concurrent RX, cold-start rollback or full platform stop. Promoting it and
comparing equivalent complete images are later work; no HAL-versus-LL resource
ranking or production replacement is claimed.

## Close work with observations

The ledger records actual implementation and evidence paths, including limited
development tests. The [development result index](../delivery/developer-experience-results.json)
keeps maintained test entry points and observed scope; final PR/CI association is
recorded after source commits exist. Final source gates, independent SDK consumption and bilingual
documentation have separate integration exits. Do not turn an expected CI run,
a template manifest or an old release result into a passed current-source exit.

Platform commit P is created before examples lock and gitlink are updated to P.
Examples commit E is then recorded with P by the delivery association. Tutorials
use an explicit examples-revision variable supplied by that record; neither
repository embeds the other repository's future commit. Normal review and
publication controls remain in effect.

No physical station is connected for this iteration. H1–H6 remain
`not_executed`: launch-board bring-up and tools; serial/SPI/I2C and recovery;
IRQ/critical-section latency; continuous DMA/Cache; Flash/watchdog/shutdown;
and final physical support sealing. Prepared plans preserve unknown PCB facts,
station identity and numeric acceptance limits for later real execution.
