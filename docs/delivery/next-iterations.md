# F4 收敛后的迭代边界

当前工作只围绕 STM32F4、实际公共消费者和精炼工程流程。全部 vendor 来源保留，
生产支持、默认构建和依赖库存分别管理。原跨系列规划从
[固定旧源码](https://github.com/X-Gen-Lab/nexus/blob/8e147fc2c812d81ab6596e0d1a6bc8908d30ac18/docs/delivery/next-iterations.md)
追溯，不作为新的生产任务清单。

| 顺序 | 退出条件 |
|---|---|
| 行为保全与清理 | 四个 F407 Board、两种密度、有效 OS 和原有模式可装配；退出平台无悬空代码、测试和命令 |
| 系列事实与驱动 | 精确型号导出 device／startup／内存，消除固定时钟、IRQ、DMA 路线和几何假设 |
| 官方库与冷态行为 | 默认 F407 冷态算法已由 C 维护；扩展完整模式时继续验证 HAL／LL、回滚和排空 |
| 默认配置链路 | 保持 Python 校验、typed IR、原子输出与输入身份；生成器只负责静态连接 |
| 精确系列覆盖 | 官方器件宏差异、完整料号与硬件 profile 分别验证，不以头文件数量代表功能支持 |
| 软件交付 | 当前源码完整门禁、实际 SDK 消费、资源比较与独立离线构建 |
| 实板接入 | 实际 station 与同一镜像的启动、时钟、IRQ／DMA、失败及测量原件 |

Host C11 配置器是 `tools/nxconfig` 中的可选主机工具试点，当前只覆盖 Linux 上的
GPIO、UART irq-byte 和 SPI poll。默认配置入口仍为 Python。Host C 全面替换不作为
平台使用、固件 C 化或本轮软件交付的前置条件；它不进入 MCU 镜像，也不会直接改变
MCU 热路径或资源占用。后续是否扩展，按实际配置需求与主机工具维护收益单独评估。

维护者按功能批次交付 C、配置、真实回归、文档和普通提交。目录移动不宣称性能改善；
新实现与旧实现须用同一工具链和等价配置比较 ELF／map 与实际热路径。

## STM32F4 全功能迭代清单

本轮以 F407VE／ZG 为首个完整验收基准，之后按精确器件扩展 STM32F4。下表是
当前实施清单；硬件存在、软件实现、Board 授权和实际验证分别记录。已有子集不能
关闭整个工作包，其他 F4 器件独有的 IP 不计作 F407 缺失功能。

装配关系继续遵循 [FIG-04](../assets/diagrams/factory-instances.svg)：主机生成静态
数据和固定连接，factory 返回已有接口，C owner 执行硬件行为。源码责任见
[FIG-31](../assets/diagrams/driver-source-ownership.svg)。资源图和触发图用于配置
校验，不在 MCU 上解释执行；新模式按需选编，不增加默认线程、heap 或全芯片对象池。

先完成 F4-01--05 的必要扩展，再用通信并发、PWM／ADC／编码器同步和显示／触摸／
存储三个纵向场景检验资源模型。随后闭合常用外设与大型外设，最后扩展电源配置和
其他 F4 器件。测试、文档和 SDK 随每个功能包交付，不集中留到末尾。

每个功能包关闭前须具备公共合同、配置选择、factory、生产 C 实现、明确 HAL／LL
归属、启停与故障回归、ARM 构建、资源预算和文档。完成一份接口头、SDK 编译或模型
测试不能替代其余条件；没有实物执行时，物理结论保持 `not_executed`。

本轮已确定 USB Device／Host 上层采用 ST 官方中间件并按需编译，公共接口隔离厂商
类型。Device v2.11.4 与 Host v3.5.3 已作为组织托管库存锁定，匹配既有 CubeF4
v1.28.3，保留 SLA0044；默认准备、编译和 SDK 均不选入。控制器适配与协议栈合同
仍待交付，不由此建立 Host／HS 或 class stack 支持。其他厂商依赖继续保留。

默认链路的启动、停止、失败回滚、资源协调与硬件算法已由手写 C 维护；固定配置和
可选诊断在编译期裁剪，通用入口复用同一实现。后续按具体需求开展精确型号适配、
运行期电源管理、完整软件候选与真实 IRQ／吞吐／栈／功耗测量。当前 F4 仍拒绝
runtime power 配置，非 F407 型号仍需精确适配。软件候选与物理状态不得从旧版本
继承，未执行的 HIL 保持 `not_executed`。
