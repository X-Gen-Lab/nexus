Nexus documentation-system architecture and delivery plan¶

Organize maintained contracts, public APIs, usage guidance and evidence into task-oriented, versioned, independently obtainable offline documentation. Reuse Markdown/public headers with Sphinx, Doxygen and Breathe, adding MyST. Product code/policy stays external.

The site, CLI, locks, prose, translations and diagram set implement this plan. Actual build/publication/recovery follows the 58-item implementation ledger and execution evidence; the migration mapping records destinations/retention. This document changes no platform support, software qualification or physical status. New/changed docs follow content/diagram standards and templates. The complete checklist derives from that ledger; diagrams distinguish current/target views.

1. 目标和边界¶

Help application developers use the platform correctly first, integrators extend it second, and maintainers/reviewers assess changes/evidence third. Readers complete definite tasks without traversing implementation history first.

  • Applications use current static instances, typed factories and C polymorphic interfaces.

  • One authored TOML is the default configuration; maintained JSON supplies SoC/Board facts.

  • Integration guidance retains context, deadlines, borrowing, draining and recovery.

  • Production support, software tests, ARM links, candidates and HIL are separate.

  • Documents, source, configuration and qualified baselines have explicit identities.

  • Maintain authoritative contracts once; other pages link/include/derive them.

  • Links/search/offline packages cover current prose; history has visible boundaries.

Docs create no product apps/tasks/private PCBs/Flash partitions/secure-update/recovery policy. Tutorials pin X-Gen-Lab/nexus-examples; platform source keeps only common fixtures/validation code. Publication does not promote models/linking into hardware qualification.

dev.py stays a thin route; docs reuse process runners, timeouts, exits and identity. docs.py/.sh/.ps1/.bat forward or state migration rather than maintaining separate generation.

  • check validates maintained sources/configuration examples without platform qualification.

  • build runs Doxygen/Sphinx in fresh outputs with -n -W –keep-going.

  • preview serves successful outputs without implicit installation/dependency replacement.

  • package verifies success/identity and seals outputs, without publishing products/platforms automatically.

  • doctor distinguishes absent tools, wrong versions and unexecuted qualification.

Preserve actual exits, diagnostics and logs. Ownership-controlled outputs cannot overwrite inputs. Old XML/HTML never substitutes for fresh success. Isolate repeated outputs/translation caches. Inject this build’s Breathe XML path rather than reading old docs/api results.

Python dependencies/wheel hashes form a separate closure, initially the executed Linux x86_64 Python tuple. Doxygen version/bytes are pinned. HAVE_DOT=NO does not mean the docs chain lacks Graphviz; pin rendering Graphviz/actual fonts too. Execute require-hashes installation in clean environments; lock files alone prove no installation.
