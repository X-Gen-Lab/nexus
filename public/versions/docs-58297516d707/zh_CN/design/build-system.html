构建系统维护合同¶

Nexus 使用唯一作者 TOML 装配、验证的不可变配置 IR、静态实例／类型化 factory 和唯一 CMake 软件目标图。Ninja 执行声明图；产品持有应用源码及组合。

48 项实施台账保留请求的退出条件。实现、已执行软件验证、环境分发及物理验收证据独立。历史源码资格不能为修改后的构建工具建立资格。

配置发布是单写入者事务，在修改所属输出前保护所有作者输入和事实输入。拒绝或中断不能把先前配置作为当前配置暴露。相同成功生成保留内容与时间戳，普通重配置不迫使无关编译。配置摘要不是编译器或生成器源码身份。

CMake 持有源码列表与目标依赖。解析器只输出所选事实和配置代码依赖，不建立平行软件构建图。ABI、优化、诊断与固件链接策略有显式目标边界。固件目标保证声明交付输出及资源检查。外部应用 warning 属消费者策略。

开发 preset 与原生 CMake/CTest 保持常规构建接口。聚焦测试用于开发反馈；commit gate 与正式资格执行完整声明 suite，生成 fresh 报告。全部 runner 保留真实 command exit、有界并发、deadline 和 process cleanup。

准备阶段可取得依赖。正式可复现性要求同一验证 source SDK、记录的环境和工具链字节进行两次全新禁网构建。Compiler cache 只改善开发，不能证明 fresh-build 可复现。持久证据保留原记录、member identity 和失败尝试，不改变历史状态。

行为修复使用实际 RED 后 GREEN。Python 工具用 unittest，C/C++ 合同用锁定 GoogleTest/GoogleMock 主机框架。CMake graph/policy 缺陷需真实小型 consumer build 与产物观察。固件保持 C11，无 host test runtime。本维护遵循正常 commit hook 和独立审查。

下表记录观察到的 host tool 与声明 lock。最终 clean-source 软件门禁和八个精确 offline candidate 见执行记录。Host 观察保持自身 scope；source qualification 使用记录的 code commit，不自动跟随后续 documentation HEAD。

实施台账保持全部 48 原要求与退出条件不变。更新路径把实现、原 RED/GREEN 和最终源码软件门禁绑定至执行记录与 结果索引。历史测量保留自身源码与精确选择，不继承后续 HEAD。

自动开发 provenance 绑定唯一不可变 command-attempt receipt 并核对命令与工作目录。完整当前合同与真实 candidate plan 执行建立该关联；共享 latest 报告名不能替代精确 attempt。
