Read exact platform support¶

Support has five separate dimensions: chip fact, maintained provider/mode, reviewed Board route, executed software scope and physical station scope. The derived capability matrix owns mode/route/ fixture/source associations. The support record owns current detailed limits; this page explains how to select them.

M0/M0+/M3/M4/M7/M23/M33/M55/M85 Core/Arch and selected baremetal/FreeRTOS software profiles; no generated SoC/Board/factory

ThreadX currently maintains Native Linux GNU and M4 GNU profiles; it does not inherit the FreeRTOS Cortex-M, MPU, split-security or tickless matrix. Platform startup does not enter either kernel. The application owns scheduler startup.

FIG-13 separates CPU software coverage from exact SoC integration and physical acceptance. FPU, DSP, Cache, MVE, SAU and IRQ width are explicit required facts; a CPU name never enables an optional capability automatically.

Check a selection before using it¶

  1. Find the exact full part and Board package, including unknown physical facts.

  2. Inspect the selected controller route and mode in the capability matrix.

  3. Resolve the actual complete assembly; unsupported modes and conflicts reject.

  4. Check software evidence for its exact source/configuration, not a nearby tuple.

  5. Check an actual station record before claiming physical behavior.

All maintained MCU physical HIL remains not executed in the current records. Default Board bindings do not cover every connector, transceiver or external part. Finite block modes include rearm gaps. Continuous modes need explicit replacement storage and service budgets; they do not promise losslessness under arbitrary load. Flash geometry is physical, while product partitions and update policy are external.

FIG-14 applies only to its declared TZEN=1 synchronous reference. It does not change the default TZEN=0 Platform configuration or establish physical isolation. Read qualification before treating any software result as a release.
