Current evidence and acceptance boundaries¶

This page describes the scope and acceptance boundaries of platform execution reports. Each iteration establishes evidence for its actual source; old candidates, historical test counts and development directories do not qualify a new HEAD. The ledger status implemented records source and tool delivery; acceptance follows the tested code identity declared in the report. Original reports retain their own output paths and bind source, configuration, dependencies, tools, command exit codes and artifacts.

See final cold-lifecycle delivery for the latest sealed 7590b2d4 platform results and public/private recovery entries. Later sections on P2, SoC/IP and other records retain their original source and historical status. Their pending fields do not override that later sealed observation, and subsequent documentation commits do not inherit firmware qualification for 7590b2d4.

Canonical commits, gates and candidate evidence from the earlier SoC extension iteration are in the SoC extension execution record; the earlier baseline record retains its original version’s evidence. These historical results keep their original source scope and do not qualify this refactor. Versioned datasheet/manual/errata indexes establish provenance only; actual silicon revisions and workaround applicability for each mode require separate acceptance. soc_costs.py retains actual ELF/disassembly/tool invocations and comparable profiles. It does not interpret size differences across backends, routes or capacities as same-configuration optimization, or instruction counts as measured cycles.

tools/hil/soc_acceptance.py provides nineteen plan/capture/validate contracts for SOC-37–55. Plan yields only prepared_unbound; reference G474/H743/U575 cannot bypass reference-only admission through renaming or recomputed metadata hashes. Actual station/tools, protocols, instruments, continuous nonempty samples and reviewed limits determine results. Physical Flash power cuts additionally require external erase-aligned test layouts outside every firmware LOAD.

Earlier development execution directories build/controller-routes-factory/ and build/minimal-factory-resources/ retain independent attempts and original commands without overwriting old runs. Resource numbers describe only the corresponding ELF; source changes require new execution. MSP is explicitly reserved and heap=0; unused memory domains do not become resident merely because a chip has them. Assembly and ELF bytes do not substitute for actual cycles/IRQ latency.

The earlier CPU/runtime development execution directory is /workspace/nexus-all-cortex-evidence. It retains original reports for CPU facts/schema, atomic publication/RMW, nine-core register models, optional-feature compilation and real kernel-context audits. Published reports record actual commands, exit codes, tools and hashes; passing counts and feature scope come from the execution results, without inheriting earlier numbers or a different combination. Source/installed Runtime consumers and full-platform consumers establish separate evidence: the former have no concrete startup, SoC, Board or factory, and cannot replace the latter or candidate sealing.

RED logs are in tools/testing/evidence/; GREEN is actual framework execution. Migration of already-correct contracts is explicitly marked; production behavior is not changed merely to manufacture RED. Commit hooks check staged snapshots/index trees at start/end, reject behavior changes during execution and publish no new success summary on failure.

Formal software qualification requires clean source/dependencies, exact tools/configuration, nonzero fresh tests, matching ELF/BIN/map, current budgets, independent source-SDK consumption and offline double-build. Exact support scope is authoritative; software-fixture connectors are not inherited by reference Boards.

All physical timing, precision, waveform, reset, power-cut and sustained-load items remain unexecuted. FP/MVE context switching, IRQ latency, cache/DMA coherence, MPU/SAU and security-world cooperation also lack physical acceptance. Optional restricted-MPU-task and split-runtime software execution cannot establish physical isolation. Actual HIL must record PCB, chip UID, probe/serial/power, station, budgets and the same candidate image.
