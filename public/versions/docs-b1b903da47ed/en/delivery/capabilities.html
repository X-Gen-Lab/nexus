Derived capabilities and integration matrix¶

tools/maintenance/capabilities.py derives this table by reading maintained soc.json, routes.json and reference-Board board.json, then running the production resolver/binding emitter on software assemblies. The table is not another configuration input. Capability changes start with original facts, implementation and regressions, then --write refreshes derived prose and --check rejects stale content.

  • Mode is a bounded SoC-declared mode; a mode without routes does not authorize connections.

  • Reviewed SoC routes describe maintained chip routes, not PCB continuity/electrical qualification.

  • Declared reference Boards means the Board has a binding, not that the default assembly enables it or physical acceptance passed.

  • Resolver fixtures are TOML software fixtures actually accepted by the current resolver.

  • Selected production source reads full ops identifiers from actual generated faces and matches initialized exported definitions in production C; comments, strings, declarations and similar prefixes are not definitions. This is bounded source-consistency evidence, not compilation/execution/physical measurement. Blank columns explicitly lack such evidence.

Rows marked native (MODEL; physical=false) project only Native software models actually selected and generated by the current resolver. They establish no physical peripheral counts, pins, IRQs, Board routes or board capability; their route and Board columns are therefore empty. Unselected host-model inventory is omitted.

The table inherits no old-candidate qualification for new HEAD and infers no physical results. The three actual Boards are disconnected; HIL remains not_executed. Exact mode limits/ownership are in support scope.

python tools/maintenance/capabilities.py --check
python tools/maintenance/capabilities.py --write

Query an exact selection and its validation stages¶

The global table helps find existing routes; product suitability requires an exact assembly. Run this read-only query from a fixed source or SDK root and select your own TOML. Successful execution prints JSON without updating the matrix below:

python tools/maintenance/capabilities.py --assembly tools/configure/assemblies/qiming-baremetal-uart-dma.toml

The report preserves the Board, full part, package, backend, clock, CPU, IRQ, physical PCB revision, memory domains, resource owners and input hashes. Controllers and endpoints each carry their selected public contracts. Additional public faces are listed separately in companion_interfaces, not represented as endpoints. DMA and pins come from this resolution, not another route in the family. This example selects finite USART1 dma-tx on F407ZG; it does not extend support to every F407 peripheral or UART mode.

validation separates the stages below. By default, the query only runs the production resolver and contract projection; it neither searches old reports nor compiles, tests, flashes or measures. Thus not_assessed means this query did not assess that stage, not that the implementation failed or was never executed historically.

Explicitly associate a sealed candidate¶

To inspect existing execution evidence, append the original candidate path to the same query:

python tools/maintenance/capabilities.py --assembly tools/configure/assemblies/qiming-baremetal-uart-dma.toml --candidate /path/to/sealed/candidate.json

The tool invokes the original candidate verifier to check all payloads, qualifications and linked artifacts, without running new tests. The report keeps both current_source and evidence.reference.source; the referenced source does not replace the current checkout. evidence.relation becomes exact_source_and_configuration only when clean commit/tree/submodules and the complete exact resolved configuration match; only then are the original candidate’s four software stages projected as passed. This is a read-only association with original execution, not a new execution.

A valid candidate from another source is marked historical_source; a different configuration is marked configuration_mismatch. Both retain not_assessed for the current selection. Missing, modified or invalid original evidence rejects the query rather than downgrading to a verified reference. Without --candidate, no Git or evidence observation is needed. Restore a portable candidate’s original closure using the existing artifact tools before providing its candidate.json; a package digest or download location alone cannot establish a passing state.

No software candidate changes physical_hil, physical_qualified=false, or family/mode rows in the aggregate table below. Hardware status still requires an actual station and observations of the same image; one passing exact configuration does not imply all Boards, backends, clocks or modes passed.
