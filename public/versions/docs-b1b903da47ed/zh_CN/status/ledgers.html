原台账、退出条件与派生视图¶

正确解读状态¶

  • implemented 表示实现存在；不保证当前 checkout 的完整软件资格。

  • development_passed 保留开发验证含义；不扩大成 clean-source 正式封存。

  • qualification_record_authority 要回到 精确结果索引。

  • implemented_tooling 只表示工装实现，物理未执行仍为 not_executed。

  • not_implemented、not_executed、失败和有条件扩展保持原值。

  • 不同专项重复覆盖同一机制，不能相加数量或计算全项目完成百分比。

platform-delivery-completion 是开发体验迭代之后的同一后续任务权威，保留 N01–N14，并追加 A01–J04 与 X01–X05 的完整工作分解。它不改写原 75 项的 退出条件或 P/E 软件执行身份；逐项完整退出条件继续保留，单个外设迁移不能关闭 整个家族任务。N11 与 H 组物理任务需要真实设备；N13 与 J 组软件封存需要当前 clean source 的完整计划和离线复现，不能由旧候选或开发测试代替。

本轮 C 冷态与工程交付观察继续写入 同一结果索引的 current_iteration_20261028。implemented 家族行表示维护路径的 C 责任已经落地， 其开发模型、ARM 和最终合并源码的资格仍分开记录。首个干净增量的 SDK／双语文档 和后续提交的普通门禁不自动覆盖新增工作树；H 组实际物理执行仍为 not_executed。

platform-refinement 保留较早的 60 项完善记录；io-evolution 是当前 42 项增量 台账。两份台账复用 IO- 编号，但来源、任务和退出条件不同，必须同时注明 CSV 或派生页面，不能按编号合并状态。增量台账的 not_qualified 保持原值；生成视图 不执行测试，也不提升软件或物理资格。

旧“48 项 OS 清单”已继续扩展。现有原 CSV 的编号为 OS01–OS55；其中 OS49–OS55 是物理工装／真实验收项，原状态均保留。构建系统的 48 项是另一个独立台账。 历史 RF 台账留在 docs/archive/implementation/，通过 历史入口 访问，不能给当前支持建立资格。

维护派生页¶

python -m tools.documentation.status
python -m tools.documentation.status --check

第一条仅由同一原 CSV 重新生成视图；第二条检查 missing／stale，失败时返回非零， 不写文件。更改原台账后应重新生成，commit／CI 检查同一派生关系。生成、检查成功 只证明文档与原字段一致，不运行固件或采集硬件。实际测试证据见原结果索引。
