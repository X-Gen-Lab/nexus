配置产品并推进 I/O¶

从外部应用教程开始。下面的命令使用同一固定 SDK 或源码检出，并从其源码根目录执行；产品 TOML、任务、缓冲区与恢复策略保留在产品仓库。解析器报告支持的软件选择，不验证连接板卡的电气事实。

选择并比较完整配置¶

编写完整装配之前先查询可选项。该查询不需要猜测后端或时钟：

python tools/configure/configure.py list-bindings \
    --board stm32f407_qiming_v31 --kind uart
python tools/configure/configure.py init \
    --board stm32f407_qiming_v31 --backend baremetal --clock hse8-pll168 \
    --profile uart --binding uart1 --instance link0 \
    --output /tmp/product-uart.toml
python tools/configure/configure.py explain --assembly /tmp/product-uart.toml

init 拒绝已有文件。empty、gpio 和 uart profile 写出可见的 TOML 值并执行正常解析器；非空 profile 需要显式 binding。被拒绝的路由不会替换为其他路由。采用波特率、事件容量、IRQ 优先级和预算前先阅读生成的 TOML。对外部 Board，init 和 list-bindings 都接受 --board-package 代替 --board。命令相对于工作目录解析包路径；init 将其写为相对于新 TOML 目录的路径。整体移动产品目录树仍保留这一关系。经过复核的 Board 包与产品装配分开维护；包内容和 provider 边界见 Board 接入指南。

解释列出公共 face、模式、时钟、资源、内存域、声明预算和执行责任。list-bindings --json 包含 mode_contracts、资源声明、fact_sources 与 limitations。binding 仍为 configuration-required：后端、时钟和全部实例必须一起通过解析。缺失的物理 PCB 事实仍未知。MCU 查询标为 not_established_by_configuration；Native 标为 not_applicable。

每个候选模式分别列出 resource_keys、occupied_resources 和 resource_scope。轮询模式不会占用备选 DMA 路由。先选 Board 的查询保留已知 SoC 和 Board 预留资源，在未选择后端时不虚构 OS owner。装配查询读取与解析输入哈希一致的事实。选项可能增加要求，因此该投影不能替代完整装配准入。使用精确支持查询区分配置接受、模型、ARM、SDK 和物理证据。

编辑独立的下一份装配后，比较有效变化：

python tools/configure/configure.py diff \
    --assembly /tmp/product-uart.toml --against /tmp/product-uart-next.toml
python tools/configure/configure.py explain \
    --assembly /tmp/product-uart-next.toml --json

两份装配都必须成功解析。diff 报告有效的平台、路由、模式、端点、存储和预算变化；只重命名源文件不构成行为变化。JSON 区分缺失字段和显式 null。以前依赖 explain 默认 JSON 的脚本现在必须传入 --json。编辑器提示仅提供帮助；解析器仍是准入权威。

diff 还把 impacts 分为 factory_ids、public_interface、transfer_contract、execution 和 storage。每项指出有效路径、变更前后值和审查责任。factory ID 变化或重排可能需要修改消费者；新执行者或 DMA 模式需要审查其生命周期和存储合同。这些是配置声明带来的影响，不是实测时序、内存节省或消费者已完成迁移的结论。

冲突诊断指出 authored 文件／key 及争用资源的 owner。修正这些输入后重新配置。不要修补生成 C、削弱 DMA reservation 或隐式改变时钟来让构建通过。配置预算是声明；宣称资源节省前必须测量实际链接镜像。见装配参考与支持矩阵。

自动化可加 --diagnostics-json，在标准错误中取得一条结构化拒绝记录并以状态码 1 退出；成功时的标准输出保持原有格式。人读和 JSON 诊断使用同一错误记录。未知或缺失字段保留上下文和键集合；资源冲突指出资源与竞争声明，包括 owner、mode 和 source。这些记录定位手写输入，不会静默修正输入。CLI 参数语法错误仍使用 argparse 诊断并以状态码 2 退出。

指定唯一执行者并保留借用存储¶

factory 返回已有的 typed face。Platform start、请求准入、执行推进、完成、恢复和停机仍是分开的操作。显式选择一种执行配方：

配方

进度责任方

存储与停机责任

主循环

循环调用选定的 service 步骤；固定 IRQ 入口执行有界 IRQ 工作

请求和缓冲区保持有效直至结清；关闭准入、取消或排空、观察结清、join observer，然后停止

独占任务

一个产品任务拥有直接操作；声明的 IRQ 策略仅允许选定的 OS 交互

显式唤醒和 service；任务超时不能撤销缓冲借用，也不能允许销毁任务栈

共享总线 owner

调用者提交有界 slot；一个 owner service 控制器和端点

队列容量、callback 与存储显式提供；关闭准入、排空已接受的 slot 和控制器引用、join observer，然后销毁 owner

这些是应用选择，不是三个隐藏驱动 worker。产品示例位于 nexus-examples：templates/{native,qiming,sky,liangshan}、apps/shared_spi_runtime 和 apps/stream_recovery。使用与平台对应的固定示例版本及其 README。SPI Native 示例与 FreeRTOS POSIX-host 演练范围不同；Native Platform 不接受 backend = "freertos"。软件双 CS fixture 不能证明首发实板存在第二条 CS 接线。

有限请求的 REJECTED 不保留调用者引用。ACCEPTED 借用请求和传输存储，直到 acquire 观察到 SETTLED。取消与 deadline 到期要求向撤销引用推进，并不结清请求。QUARANTINED 保留存储及清理义务。SETTLED 不表示传输成功，也不表示 callback 和 observer 已 join。在栈上放置异步存储或停止 worker 前先阅读所有权。

对于 stream，消费者显式释放每个取得的块。慢消费者可能按选定模式造成 loss 或因背压停止；provider 不得覆盖未归还的借用块。在借用块与硬件引用排空前 stop 可以返回 BUSY。完整停止后以新的有效生命周期 restart；清除计数器不等于恢复。H743 连续模式演练使用独立的精确 ARM 配置，不声称三块首发板具有相同的连续模式接线。

诊断事实，不改变所有权¶

nexus/io/diagnostic.h 中的 nx_io_diagnose 组合复制的 request 和 stream 观察，以及明确已知的生命周期、owner、service 时间与 observer 事实。它既不读取实际 MMIO，也不调用 service 或恢复。独立 finding 位可以并存；unknown_facts 保留缺失信息。没有 finding 不构成健康证明。

request 停止推进不能证明遗漏 service 循环。SERVICE_OVERDUE 需要同一单调时钟域的有限时间戳及正的最大间隔声明；时间倒退以 STATE 拒绝。只有成功取得 owner 诊断快照，准入字段才算已知。仅凭 BUSY 不能证明队列满。未结清 stream 块可以属于生产者、ready 或消费者；普通 cursor 不说明私有预投递 slot。应用仍拥有重试、安全输出与复位策略。

nx_dma_storage_validate 将完整的显式 reservation 与 payload 分开验证。例如17 字节 payload 可以放在调用者拥有、按32 字节 cache line 对齐的64 字节 reservation 中。完整 reservation 必须已经满足声明的 DMA 可达域和完整行所有权。该函数不取整、不分配、不 bounce、不执行 cache 维护，也不替代 provider 模式准入。deadline 到期绝不允许在排空前重用 reservation。

可选 owner 观察增加 accepting、queued 和 slot_available。其公共 observation／sidecar 布局已改变，消费方须重新编译。默认 owner 与 provider 结构不增加这些字段。按选定 ABI 测量可选 sidecar 存储，不能假定它没有成本。

日常设备操作计划与资格验收分开¶

对于 flash／debug，使用已识别的设备文件和实际成功构建的 provenance。Monitor 可以不关联构建：

python tools/dev/dev.py flash --target /path/equipment.json \
    --provenance /path/build-provenance.json --elf /path/application.elf
python tools/dev/dev.py debug --target /path/equipment.json \
    --provenance /path/build-provenance.json --elf /path/application.elf
python tools/dev/dev.py monitor --target /path/equipment.json \
    --provenance /path/build-provenance.json

默认只打印计划。实际执行需要 --execute --output 与新的自有目录。Flash／debug 要求相符的板卡／料号、镜像、探针序列号及固定工具／配置字节，不要求串口控制台。Monitor 需要板卡、稳定的 serial by-id 和测试站锁，可以省略构建 provenance；此时结果标为 image_linkage = unassociated，不构成关联镜像的观察。Monitor 使用115200 8N1 和有限时长；EOF 或断连失败。Debug 仅绑定 loopback。失败或取消的设备操作保留锁供显式检查；正常完成释放锁。日常操作成功不构成 HIL 资格。真实设备未连接前，物理执行记录为 not_executed。性能与 HIL 指南负责采集和资格合同。
