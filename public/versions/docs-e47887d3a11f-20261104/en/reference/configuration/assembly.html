Assembly input and rejected selections¶

The authored configuration authority is one schema-2 TOML assembly. SoC and Board facts remain maintained JSON; resolved.json is output, not an authored alternative. CMake owns software dependencies. Failed TOML resolution never falls back to Kconfig, cache variables, schema-1 JSON or old generated headers. Legacy JSON assemblies are rejected as inputs, not retained as an alternate authoring interface.

The parser creates immutable AuthoredAssembly intent. Production consumers use resolve_ir() and named immutable ConfigurationIR decisions; only audit and artifact-boundary consumers request to_dict(). Typed source epoch 2 and the schema-1 JSON output projection are separate contracts. The source compatibility policy owns their version declarations; neither introduces firmware metadata or runtime dispatch.

Before running the resolver, prepare the fixed source and recursive dependencies.

Physical Flash and the selected image¶

flash in the resolved output describes the complete physical device, including its exact erase and programming geometry. layout selects the physical erase owner that contains the executable image. Without an authored layout, that owner is the complete physical Flash. Products still own writable regions and recovery; this selection grants no Flash access control or protection.

A layout JSON file has schema_version = 1 and regions. Each region has an id, integer origin, positive size and kind (image or data). Exactly one region is an image. IDs must be unique; all regions must be nonoverlapping, within physical Flash, and start/end on its exact erase boundaries. This is an auxiliary layout input; schema-1 JSON assemblies remain rejected.

Executable prefix and suffix¶

The optional [memory] fields reserve bytes inside the selected physical owner. Both fields are unsigned 32-bit byte counts with a default of zero. Booleans, floats, negative values and values above 4294967295 reject. Zero-valued fields are omitted from the resolved projection. They preserve the existing default layout, linked addresses and budgets; source changes still change source and configuration identities.

Field

Meaning

image_prefix_bytes

Reserved bytes before the executable vector table

image_suffix_bytes

Reserved bytes after the executable load window

ConfigurationIR derives the executable origin and size from its immutable FlashRegionIR owner and MemoryBudgetIR reservations. PhysicalPartIR remains the sole physical geometry authority; the JSON layout projection retains that geometry for audit. No independent executable address or CMake address override is authored.

owner       = [layout.origin, layout.origin + layout.size)
image_start = layout.origin + image_prefix_bytes
image_end   = layout.origin + layout.size - image_suffix_bytes
image_size  = image_end - image_start

The physical owner remains erase-aligned and nonoverlapping. Its executable window need not start on an erase boundary. The prefix plus suffix must be less than the owner size and leave a complete reset vector. The derived window must stay inside that owner without address overflow. An explicit flash_load_limit_bytes cannot exceed the executable size; the default Flash budget uses that size. Reserved prefix/suffix bytes do not count as actual ELF LOAD bytes and do not change the physical Flash API.

The reviewed offset and nonzero-reservation profiles are STM32F407VET6, STM32F407ZGT6 and GD32F470ZGT6. They require complete physical erase geometry and a 512-byte-aligned executable vector base, including when the physical owner starts at the reset address. Other SoCs and external provider packages gain no prefix/suffix support from these fields. The maintained profile owns that exact alignment and its actual vendor vector symbol; authored or artifact metadata cannot grant another startup that capability.

For example, this complete layout file selects the final 384 KiB of Sky STM32F407VET6 Flash. Select it with the assembly’s layout path. The decimal origin is 0x08020000; the omitted first 128 KiB is not another selected image and is not protected from writes by this layout.

{
  "schema_version": 1,
  "regions": [
    {
      "id": "application",
      "origin": 134348800,
      "size": 393216,
      "kind": "image"
    }
  ]
}

For an offset image or nonzero reservations, generated linker checks require .isr_vector at the derived executable origin, correct alignment, a nonempty table no larger than 512 bytes, and the actual vendor symbol at the section base: g_pfnVectors for F407 or __gVectors for GD470. The reviewed startup sets VTOR from that linked symbol with the required barriers. Default zero-reservation reset-address linking keeps its existing semantics.

ELF LOAD bounds, Flash capacity and footprint use the derived executable window. The resource checker independently validates the physical owner, reservations, vector words, reset entry and all actual Flash LOAD ranges against that window. ELF-to-BIN checks reconstruct bytes from the executable origin. They add no prefix or suffix bytes. Physical erase/program facts and RAM budgets remain unchanged; use flash, not layout.origin, to interpret erase geometry.

The complete public image-window reference selects a 128 KiB F407 sector owner at [0x08020000, 0x08040000). Its 512-byte prefix and 1,024-byte suffix derive [0x08020200, 0x0803fc00), or 129,536 bytes, for vectors and executable LOADs. The reference links the actual reviewed startup through the installed SDK; its declared 2,048-byte MSP is not a measured stack peak.

A prefix reservation does not create an image header. A suffix reservation does not create a trailer, activation marker or rollback record. Products supply any metadata format, keys, Flash permissions and recovery policy. The platform does not build a bootloader or authenticate, install, activate or boot this image.

An offset executable still needs a product-owned boot path that reaches its vendor reset entry with valid initial machine state. Linking, vector checks and BIN identity do not execute that path. This mechanism does not provide image authentication, activation, A/B rollback, Flash permissions or a general running image handoff. Baremetal or FreeRTOS links prove their build scope only. In particular, the existing F407 handoff retains PRIMASK=1 and startup does not unmask it; no FreeRTOS handoff qualification follows from an offset link.

Inspect and generate¶

Run from the repository root, using a new output you own:

python tools/configure/configure.py list-bindings     --assembly tools/configure/assemblies/native-uart.toml
python tools/configure/configure.py check     --assembly tools/configure/assemblies/native-uart.toml
python tools/configure/configure.py explain     --assembly tools/configure/assemblies/native-uart.toml
python tools/configure/configure.py generate     --assembly tools/configure/assemblies/native-uart.toml     --output /tmp/nexus-native-config

check and explain do not generate output. generate publishes one atomic owned bundle; failure invalidates its owned output without replacing unrelated data. Inspect resolved.json, input identities, generated nexus_config.h, bindings, factory, linker memory and budgets. Changing declared inputs requires a fresh resolution; separate Board/backend combinations use separate build roots.

CPU-only Runtime has a separate authored runtime TOML using the shared CPU resolver. It emits Core/Arch/optional OS policy, no SoC/Board/startup/factory. Do not use it to claim a full device platform. The build contract, integration contract and production field model/schema own detailed accepted fields; editor completion does not establish hardware capability.
