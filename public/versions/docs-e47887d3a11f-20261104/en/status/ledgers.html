Interpret statuses correctly¶

  • implemented means implementation exists; it does not guarantee complete software qualification for the current checkout.

  • development_passed retains its development-validation meaning; do not expand it into formal clean-source archiving.

  • Consult the exact results index for qualification_record_authority.

  • implemented_tooling only means tooling is implemented; unexecuted physical work remains not_executed.

  • not_implemented, not_executed, failures and conditional extensions retain their original values.

  • Different workstreams cover overlapping mechanisms; do not add their counts or calculate project-wide completion percentages.

platform-delivery-completion remains the same follow-up task authority after the developer-experience iteration. It preserves N01–N14 and adds the complete A01–J04 and X01–X05 work breakdown. It does not rewrite the original 75-task exit conditions or P/E software identities. Each full exit remains intact; migrating one peripheral cannot close a whole-family task. N11 and the H-group physical tasks require real equipment. Maintain derived pages¶

python -m tools.documentation.status
python -m tools.documentation.status --check

The first command only regenerates views from the same original CSV. The second checks missing/stale output, returns nonzero on failure and writes nothing. Regenerate after changing original ledgers; commit/CI checks the same derivation relationship. Successful generation/checking only proves documentation matches original fields; it executes no firmware and acquires no hardware observations. Actual test evidence is in the original results indexes.
